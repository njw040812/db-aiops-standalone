# 面试 Q&A（项目事实版）

> 只回答「这个仓库里真的有」的东西。每题都能指向代码或评测脚本。
> 如果面试官问到大模型、Kafka、多副本，答案统一是「做了抽象/留了扩展点，没在生产验证」。

---

## 一、项目事实

### Q1：简单介绍一下这个项目。
个人项目，面向 MySQL 一主两从场景，把「告警 → 根因 → 修复提案 → 变更审批 → 执行 → 审计」
做成一条可回放的流水线。Python 单语言，4 个 Agent、5 个节点，默认不依赖 Kafka/Neo4j。

### Q2：为什么做这个方向？
数据库运维里最耗时的不是执行命令，而是凑证据和等审批。我想验证一件事：
把变更管理做成代码之后，自愈的安全边界应该画在哪。

### Q3：项目规模？
18 个源码文件、约 4000 行；108 个 pytest 用例；3 个评测脚本；14 个 DBA Playbook；
知识图谱 13 节点 17 边。

### Q4：上线了吗？有生产数据吗？
没有。执行器默认模拟，评测是合成数据。简历和面试里都不宣称线上 MTTR 收益。

### Q5：你负责哪部分？
全部：架构、四个 Agent、编排器、图谱、审计、API、测试和评测。

### Q6：技术栈？
Python 3.10、FastAPI、Pydantic v2、NumPy、scikit-learn、pytest；MySQL 8.0 作为业务背景；
Kafka/Neo4j 只做了适配层。

### Q7：为什么只有 Python？
面试方向是数据库运维，Python 足够表达算法和流程；三语言实现会把精力摊薄，
而且初版 README 声称的 Java/Go 代码并不存在，已经删掉了。

### Q8：这个项目最能体现你能力的一点？
把「自动化」拆成「提案」和「执行」两段，并用测试锁死所有绕过审批的路径。

## 二、架构与编排

### Q9：为什么用状态机而不是线性 Pipeline？
线性 Pipeline 处理不了条件分支：根因置信度不足要停、审批 pending 要中断、
执行失败要回滚、同一节点要重试。状态机把这些显式化，也方便断言节点状态。

### Q10：为什么选 Orchestrator 而不是 Choreography？
故障处理需要「谁在什么时候做了什么」的强顺序和审批中断点，中心编排更好调试。
代价是编排器是单点，生产要配多副本和检查点持久化。

### Q11：节点失败后怎么办？
重试（默认 1 次），仍失败就终止整个工作流，状态置 failed。
不会在根因失败后继续执行自愈——那是初版的 bug，已经用 `test_failure_halts_workflow` 锁住。

### Q12：检查点怎么做的？
每个节点完成后对 `IncidentState` 做深拷贝，按 incident_id 存内存。
`resume()` 从断点继续，人工审批后只跑 execute 节点，不重跑监控和根因。
外部 `get_checkpoint()` 返回副本，避免调用方改坏内部状态。

### Q13：重试计数为什么容易写错？
如果计数挂在共享的节点对象上，第二个故障会继承第一个的重试次数。
我把节点定义（NodeSpec）和单次运行记录（NodeRun）分开，按 incident 隔离。

### Q14：事件总线在这里起什么作用？
Agent 之间不直接调用，通过 topic 广播；审计 sink 订阅 `aiops.audit` 落盘。
默认内存实现，Kafka 实现用 `asyncio.to_thread` 包住阻塞的 produce/poll。

## 三、异常检测

### Q15：为什么不用固定阈值？
固定阈值要么太松（漏报早期劣化），要么太紧（业务高峰误报）。
但固定阈值不是没用：它表达业务容忍度，所以严重度分级仍以静态阈值优先。

### Q16：为什么用 MAD 而不是 3-Sigma？
慢查询、主从延迟是长尾分布，均值和标准差会被历史尖刺拉偏；
中位数和 MAD 对离群点不敏感，鲁棒性更好。

### Q17：为什么只检测上冲？
主从延迟、连接数使用率、磁盘使用率只有变高才危险。双向检测会把「延迟归零」判成异常，
这是运维语义上的误报。

### Q18：冷启动怎么处理？
历史样本不足 20 个点时，Monitor 只记录不判定；单个算法样本不足时弃权，
投票只统计有结论的算法。避免拿 3 个点算出「异常」。

### Q19：多算法投票怎么定阈值？
至少 2 个算法同时判异常才报警。代价是召回略降，换来误报从千分级降到 0.8‰。

### Q20：检测效果怎么评估的？
自建回放集：5 个指标 × 600 点，16 个注入窗口（含 1 个 CPU 骤降）。
逐点算 TP/FP/FN、每千点误报、窗口检出率、首告警时延。结果：检出率 94%、时延中位 0 点、误报 0.8‰。

### Q21：为什么静态严重阈值检出率只有 69%？
因为部分窗口的峰值没到 crit 阈值。这正是动态检测的价值：在越线之前发现趋势。

## 四、根因与图谱

### Q22：知识图谱里有什么？
节点：服务、网关、代理、数据库、缓存、主机；边：DEPENDS_ON、REPLICATES_FROM、RUNS_ON。
演示拓扑是 13 节点 17 边，主从关系是一主两从。

### Q23：根因怎么算的？
反向 BFS 找依赖叶子 → 收集证据（指标、24h 变更、共置主机、长事务/慢查询/日志）→
每个假设 `prior × likelihood` → 归一化成后验 → 取最高分。

### Q24：为什么后验要归一化？
不归一的话多个候选可能都接近 1.0，无法设阈值，也无法比较领先差距。
归一化后 Σposterior = 1，才可以规定「低于 0.30 或领先不足 0.05 就转人工」。

### Q25：影响面怎么算？
从目标节点沿反向依赖边 BFS，统计可达的服务节点数 / 服务节点总数。
主库是 1.0，副本 0.4，报表服务 0.2。

### Q26：为什么证据不足要转人工？
自愈最大的风险不是修不好，而是证据不足时仍然自信地执行破坏性命令。

### Q27：Neo4j 里怎么查多跳依赖？
Cypher 的 `MATCH path = (s)-[:DEPENDS_ON*1..N]->(root)`。
注意 N 不能参数化，必须转成整数再拼接；节点标签和关系类型走白名单防注入。

## 五、自愈、审批与审计

### Q28：为什么把自愈拆成两阶段？
因为「提案」和「执行」的责任主体不同。提案可以由 Agent 做，执行必须有人批准。
两阶段也让 dry-run 有地方放。

### Q29：怎么保证没人能绕过审批？
三层：编排器只在 approved 时路由到 execute；`HealAgent.execute()` 第一行校验审批状态，
否则抛 `PermissionError`；执行前还有幂等检查和熔断器。

### Q30：dry-run 做了什么？
检查命令非空、首 token 在白名单、不命中危险模式（DROP TABLE、rm -rf、管道、命令替换）。
它不连数据库，也不执行 SQL。

### Q31：风险模型怎么设计的？
6 个因子：爆炸半径 0.30、操作风险 0.25、变更窗口 0.15、实例关键度 0.10、
历史成功率 0.10、数据丢失 0.10，权重和为 1。L0 ≤0.30 自动，L1 ≤0.55 当班，L2 必须工单。

### Q32：为什么 DDL 在业务时段要挂起？
在线 DDL 会消耗 IO、持有元数据锁，风险随时间放大。系统里 `requires_window` 的操作
在 8:00–22:00 直接挂起，等窗口。

### Q33：熔断器什么时候打开？
连续 5 次执行失败后 OPEN，60 秒后进入 HALF_OPEN 放一个探针；成功则 CLOSED，失败继续 OPEN。

### Q34：审计为什么要哈希链？
普通日志可以被静默改掉。每条记录带 `prev_hash` 和 `hash`，删一行或改一个字段，
后续链条就对不上，校验能定位到文件和行号。

### Q35：执行失败怎么回滚？
Playbook 可选 `rollback_command`，失败时执行并记录结果；回滚也失败会写进审计并打开熔断。
不是所有操作都可回滚（KILL 会话就不可逆），所以才有 L2。

## 六、数据库运维常识

### Q36：主从延迟常见原因？
大事务、从库执行 DDL、从库资源被抢占、单线程回放瓶颈、网络抖动、主库写入突增。
本项目的故障目录覆盖了这五类。

### Q37：连接数打满怎么排查？
看 `Threads_connected` 与 `max_connections` 比例、`SHOW PROCESSLIST` 里的 Sleep/Query 分布、
连接池配置、慢查询是否长期占用连接、是否有连接泄漏。

### Q38：在线加索引怎么做？
gh-ost / pt-online-schema-change，先影子表、增量同步、切换；必须评估磁盘、IO、
主从延迟和锁等待，放在变更窗口做。

### Q39：慢查询优化思路？
先看执行计划和扫描行数，再判断索引缺失/失效、统计信息过期、回表过多、排序临时表；
不是所有慢查询都加索引，有时要改 SQL 或归档。

### Q40：备份恢复怎么验证？
定期做恢复演练，而不是只看备份任务成功；校验 binlog 位点、恢复耗时、数据一致性。

## 七、反思与边界

### Q41：这个项目最大的不足？
没有真实数据源和执行环境。检测和根因的有效性只经过合成数据验证，真实环境会有
指标缺失、标签漂移、审批流程差异。

### Q42：如果接 LLM，接在哪？
接在候选排序和报告生成，不接在命令生成。输入是结构化的假设、证据、置信度，
输出是排序和解释；执行仍然走 Playbook 与审批。

### Q43：如果多实例部署，哪里会坏？
去重指纹、熔断状态、审批锁都在进程内；需要外置到 Redis/DB，并用分布式锁保护 resume。

### Q44：为什么保留模拟执行器？
默认安全。真实执行需要显式环境变量开启，且只允许白名单命令。
面试时我宁愿说「没连过生产库」，也不愿暗示「修复成功」。

### Q45：这个项目对你面试数据库运维岗位的帮助？
它逼我把变更管理、审计、告警分级这些平时靠流程保证的东西写成代码，
反过来也让我更清楚流程里每个卡点的意义。
